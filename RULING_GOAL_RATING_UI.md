# Gate 1 Ruling: Goal/Rating creation UI

Both plans independently re-verified my brief's central security claim (confirmed, real, exploitable) and then each found real additional gaps I missed — Sol found a bypass that would have made Jcode's own fix trivially defeatable. This ruling is larger than the original brief because the review process did its job. Execute against this contract; it supersedes the brief wherever they conflict.

## Confirmed and adopted from both plans (no disagreement)

1. **The core gap is real**: an employee can currently write `goal.manager_rating`/`manager_comment` directly via UPDATE, since `goal_participant_update`'s `with check` tests row-reachability, not which columns changed, and `restrict_manager_goal_updates` only fires for a caller who qualifies as the *manager*. Close it as briefed: `restrict_employee_goal_updates()`, mirroring the existing trigger's exact shape, blocking `id`, `kra_category_id`, `manager_rating`, `manager_comment`, `created_at` (both plans independently included `id` in the block list — do so).
2. **Manager plan-review transition**: new helper `can_manager_mark_plan_reviewed(plan_id)`, new RLS policy `employee_goal_plan_manager_mark_reviewed`, new trigger `restrict_manager_plan_status_transition()` allowing only `submitted → manager_reviewed`, blocking every other column **including `published_at`** (Sol's catch — it exists on the table by the time 0017 runs even though 0001 didn't define it; the trigger's "everything else unchanged" set must name it explicitly, not just implicitly cover it) — `id`, `review_cycle_id`, `employee_id`, `overall_rating_scale_max`, `created_at`, `published_at`, all blocked; only `status` may change, and only `submitted → manager_reviewed`.
3. **RLS-blocked updates fail silently.** A caller outside the policy's `using` clause gets zero rows affected, not an exception. Every verify.sql assertion for "rejected outside the right window" must assert row-count zero, not expect a raised error — and the frontend must do the same: any critical status-transition call needs `.select("id,status").single()` (or equivalent) and treat "no row came back" as a real, user-facing error, not a silent no-op.
4. **Submit-flow ordering**: persist ratings → compute the rollup (`compute_goal_plan_rating`, idempotent via upsert) → *then* flip status. Not "flip status then hope the rollup call succeeds" — that stranding risk is worse on the manager side, where `manager_reviewed` is no longer manager-editable if the rollup call fails after the status already moved. Apply this ordering to **both** the employee self-submit flow and the manager mark-reviewed flow.

## Additional fixes required — Sol's findings (must-fix, not optional)

5. **INSERT-side bypass — this is the most important addition to the brief.** `goal_employee_insert`'s `with check` is currently just `can_edit_kra_category_as_employee(kra_category_id)` — nothing stops an employee from inserting a *brand-new* goal row with `manager_rating`/`manager_comment` already populated. A BEFORE UPDATE trigger does nothing against an INSERT. **Tighten the policy itself** in 0017:
   ```sql
   with check (
     public.can_edit_kra_category_as_employee(kra_category_id)
     and manager_rating is null
     and manager_comment is null
   )
   ```
   HR's `goal_hr_all` policy is a separate `for all` OR-path and is unaffected — HR can still insert pre-rated rows administratively if ever needed. Without this, item 1's fix is cosmetic: anyone can route around the UPDATE trigger by inserting instead.

6. **`can_manager_rate_goal` ignores plan status entirely.** It only checks `review_cycle.status = 'manager_eval'` — a manager can currently rate a goal on a plan that's still `draft` (never submitted), or keep changing ratings after the plan is `manager_reviewed`/`finalized`, as long as the cycle-wide window is open. This undermines the entire point of the submit gate. **Tighten the function**: add `and (select status from public.employee_goal_plan where id = (select employee_goal_plan_id from public.kra_category where id = (select kra_category_id from public.goal where id = p_goal_id))) = 'submitted'::public.goal_plan_status` (or a cleaner join — your call on the exact SQL shape, just land on the same semantic: manager-rate is only possible while the specific plan is `submitted`, not merely "sometime during the cycle's manager_eval window"). This function is also read by `restrict_manager_goal_updates`, so the tightening applies everywhere that trigger already runs — no separate change needed there.

7. **The employee's own plan-status-update policy has the same column-scope gap as the pre-fix goal table did.** `employee_goal_plan_employee_update`'s `with check` only re-tests `employee_id`/`status`/participant — nothing stops an employee from also changing `review_cycle_id`, `overall_rating_scale_max`, or `created_at` in the same UPDATE call that flips `status`. Close it with a mirrored trigger: `restrict_employee_plan_status_updates()`, same idiom, HR bypass, then for a caller who is `can_edit_goal_plan_as_employee(old.id)`, allow **only** `status` to change (the RLS `with check` already constrains it to `draft`/`submitted`), block `id`, `review_cycle_id`, `employee_id`, `overall_rating_scale_max`, `created_at`, `published_at`. This gives both the employee and the manager side of `employee_goal_plan` a real column-scoped trigger — do both in this migration, not just the manager one the brief asked for.

8. **Seed ID correction — my brief was wrong, Sol is right (independently verified against `seed.sql` directly):** Lina Chan's plan is `33333333-...000c` and holds the **cascaded** copy of Ana's goal (`goal_cascade`, top-down). Rith Pen's plan is `33333333-...000d` and holds his own **independently authored, later aligned-upward** goal (`goal_alignment`, bottom-up) — not a cascade. Both are unrated (self/manager both null), but they exercise different relationship types. Use the correct IDs in any fixture/test that references them.

## Additional fixes required — Jcode's findings (must-fix, not optional)

9. **`rating_scale_max` footgun.** It's on the employee-editable column list (legitimately — it's part of goal structure), but it's also the CHECK bound for `manager_rating`. An employee lowering it after a manager has already rated either produces a confusing `23514` (if the now-out-of-range manager_rating gets touched some other way) or, worse, silently rescales what a submitted manager rating *means* with no visible change to the number itself. **Add to `restrict_employee_goal_updates()`**: if `new.rating_scale_max is distinct from old.rating_scale_max and old.manager_rating is not null`, raise `42501` — lock the scale once a manager rating exists, even though the column is otherwise employee-editable.

## Decided, not adopted

10. **Dual-role edge case** (a person who is both the plan's employee *and* a `line_manager` participant on the same plan — not schema-prevented, unusual but possible): both triggers would independently fire and such a person would be locked out of writing either side's columns during their own overlapping window. **This is the correct conservative outcome, not a bug** — resolving it "properly" would require a role-precedence policy decision (which hat does the person wear?) that's a business call, not an engineering one, and genuinely out of scope for this round. Document it plainly in the migration's header comment so a future reader isn't confused; a verify.sql assertion for it is a nice-to-have, not required — include one only if it's cheap to add alongside the other fixture work, skip it otherwise rather than let it inflate scope.
