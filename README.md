# okr-kra-pms

A proof-of-concept schema for a web-based performance management system covering both **KRA** (Key Result Area) scorecards and **OKR** (Objectives & Key Results) tracking — the two frameworks most mid-size orgs run in parallel, and the two most performance-management tools (SAP SuccessFactors, Oracle Fusion HCM, Workday, Lattice, Betterworks) keep structurally separate rather than merging into one score.

This repo is schema-first: Postgres migrations + Row-Level Security policies for a Supabase backend, built and cross-verified by two independent AI coding agents (Jcode/Claude and Codex/GPT-5.6) with an adversarial cross-challenge round before anything merges, and a live `supabase db reset` + RLS/rollup verification pass before anything ships. See `VERIFICATION.md` for the actual test queries and expected results.

## Design decisions

- **KRA drives the appraisal number, OKR is a strategic overlay.** KRA goals roll up into one weighted rating (Oracle's "Average Method"); OKR key results carry their own 0.0–1.0 score and feed evidence into the same review without being mathematically merged into the KRA rating.
- **Cascade and align are different relationships**, not one generic parent-goal pointer — a cascade copies a manager's goal down to a report; an alignment links two independently pre-existing goals, one link up per goal, many down.
- **Matrix management is a first-class, explicitly-scoped role** — a matrix manager can rate only the specific KRA categories they've been granted, keyed off an explicit grant row, never off the role name alone.
- **Every RLS policy is keyed off an explicit participant/grant table** (`review_participant`, `review_participant_scope`), never off a bare role name or job title — this was a deliberate response to a documented SAP SuccessFactors permissioning quirk where a broadly-granted role surfaced UI for people it shouldn't have applied to.
- **Calibration is a human-facilitated override, never an algorithm.** Every vendor researched (SAP, Workday, Lattice, Betterworks) explicitly avoids forced-distribution normalization — `calibration_participant` stores the pre-calibration snapshot (`original_score`, immutable) alongside the HR-adjusted value (`calibrated_score`) as the audit trail, and nothing auto-curves anyone's rating.
- **The employee never sees a calibrated/final score until HR explicitly publishes it** (`employee_goal_plan.published_at`) — even mid-calibration, even after the manager's raw rating is already visible. Publishing itself is blocked while the plan's calibration session is still open, so a published score can never be a stale, un-finalized number.
- **Comp export is deliberately more restricted than day-to-day review visibility.** A line manager can already see their own reports' individual reviews, but `comp_export_rows` gates on `is_hr_admin` explicitly — compensation-cycle data gets a narrower circle than performance-review data, as a deliberate governance boundary, not an oversight.
- **A published score is a one-way door.** Building the facilitator UI surfaced a real hole in the original Phase 3 functions: nothing stopped a published plan from being added to a *second*, still-open calibration session, silently changing the employee's already-visible published score without a new publish action. `add_plan_to_calibration_session` now rejects that outright (`published_at is not null` → `55000`), and `calibration_eligible_plans` excludes published plans from the picker so HR never sees the option in the first place.
- **RLS row-visibility and column-write scope are two different guarantees, and only one of them existed for the goal-rating workflow before this round.** `goal_participant_update`'s `WITH CHECK` had always tested "can this caller reach this row," never "which columns did they change" — so an employee who could legitimately edit their own goal could also silently write `manager_rating`/`manager_comment` directly, and could insert a brand-new goal pre-populated with a fake manager rating (the INSERT policy checked category ownership only, not column contents). Both are closed now: a mirrored `restrict_employee_goal_updates()` trigger column-scopes the employee's UPDATE path exactly like the pre-existing manager trigger already did, and `goal_employee_insert`'s `WITH CHECK` now requires `manager_rating`/`manager_comment` to be `null` at creation time. `can_manager_rate_goal` was also tightened to require the specific plan's status be `submitted`, not just "the review cycle is somewhere in its manager_eval window" — a manager could previously rate a goal on a plan the employee hadn't submitted yet, or keep changing ratings after the plan was already `manager_reviewed`.
- **A review cycle's status is a one-way lifecycle, not a free-form field.** Before Round 2, `review_cycle_hr_all`'s blanket `for all` grant meant HR could set `status` to any value in any order via a raw API call — skip straight to `closed`, or reopen a closed cycle — with nothing in the database to stop it. `restrict_review_cycle_status_transition()` now enforces the exact `draft → active → self_eval → manager_eval → closed` sequence, one step at a time, for every caller including HR, raising `55000` (not `42501` — this is an invalid-state error, not a permission error, and the two are kept distinguishable end to end). New cycles must be inserted as `draft`. Once `closed`, a cycle is frozen for good: objective/key-result/check-in writes against a closed cycle are rejected at the trigger level too, including for HR, so "closed" actually means closed rather than just hidden by the UI.
- **OKR progress has exactly one legitimate writer: the check-in trigger.** Before Round 2, an objective owner could `UPDATE key_result SET current_value = ...` directly, bypassing the check-in history entirely — the score would look real but have no event behind it. `restrict_key_result_owner_updates()` now blocks direct `current_value`/`score` writes from anyone, including HR (HR still sets `score_override` for a manual override, which is a different, explicit column). The guard distinguishes a direct client UPDATE from the check-in trigger's own legitimate propagation UPDATE via `pg_trigger_depth()` (depth 1 for a direct call, depth 2 when the write originates from inside `apply_check_in_to_key_result`'s own AFTER INSERT trigger) — a regression test in `verify.sql` pins both sides of that distinction so a future change to either trigger can't silently break the other. `check_in` itself is now append-only end to end: `checked_in_by`/`created_at` are force-set server-side regardless of what a client sends, and the previous blanket HR policy (which allowed HR to silently edit or delete check-in history) is replaced with HR read-only — check-ins are the evidence trail behind OKR progress, and a record that can be quietly rewritten after the fact isn't a record.
- **A self-referencing RLS `SELECT` policy can fail against the very row it just inserted.** Building the objective-creation UI surfaced a latent bug that had existed since Phase 2 and was simply never exercised: `can_read_objective()`'s "am I the owner" branch re-queries `objective` by id, and when that function is invoked as part of the `SELECT`-policy check Postgres performs for `INSERT ... RETURNING` (what `.insert().select()` issues), the self-referencing subquery runs under a snapshot taken at the start of that same statement — before the row it's looking for exists. A plain `INSERT` without `RETURNING`, or a separate follow-up `SELECT`, both work fine; only the same-statement create-and-read-back path was broken, which is exactly the shape every insert-returning-the-new-row UI action uses. Fixed in `0019` by checking `owner_id = auth.uid()` directly in the `USING` clause — a `USING` clause has direct access to the row's own columns and needs no subquery for the self-owned case — before falling back to `can_read_objective()` for the manager/matrix-manager cases, which read an already-committed parent row and aren't snapshot-fragile. `key_result`'s and `check_in`'s `SELECT` policies were checked for the same pattern and don't have it — both key off their *parent* row's id, which already exists under any snapshot, not their own.

## Local development

Requires Docker Desktop.

```bash
npm install
npx supabase start
npx supabase db reset   # applies all migrations + seed.sql
```

Local Supabase ports are remapped to `15420`–`15429` in `supabase/config.toml` (the CLI's 54320s defaults fall inside a Windows Hyper-V dynamic port-exclusion range on the machine this was built on — harmless on other platforms, left as-is for portability).

Studio: `http://127.0.0.1:15423` · API: `http://127.0.0.1:15421` · DB: `postgresql://postgres:postgres@127.0.0.1:15422/postgres`

### Automated verification

`scripts/verify.sql` is an assertion suite (RLS coverage across all 18 tables, the rollup regression guard, the matrix-scope join, the check-in scoring trigger, every Ruling fix across all three phases, the calibration finalize/publish gates, the comp-export HR-only boundary, the facilitator UI's HR-gated read RPCs, atomic session creation, and published-plan recalibration guard, the goal/rating workflow's employee/manager column-scope guards and status-transition gates, and the review-cycle lifecycle guard, closed-cycle write freeze, key-result column-scope guard, and check-in immutability from Round 2 — 72 assertions) that runs against a freshly-reset database and fails loudly on any mismatch:

```bash
psql "postgresql://postgres:postgres@127.0.0.1:15422/postgres" -v ON_ERROR_STOP=1 -f scripts/verify.sql
```

The same script gates every push in CI (`.github/workflows/ci.yml`).

## Frontend

`web/` is a Next.js (App Router) + Tailwind v4 app. The employee review summary (`/review`) is the landing screen — KRA scorecard and OKR objectives/key results side by side, backed by the `employee_review_summary` RPC and enforced end-to-end by the RLS policies above (log in as a different seeded user and you see a different, correctly-scoped result).

```bash
cd web
npm install
cp .env.example .env.local   # fill in NEXT_PUBLIC_SUPABASE_ANON_KEY from `npx supabase status`
npm run dev
```

Local seed credentials: `dara.sok@example.com` / `password123` (or any other seeded user — see `supabase/seed.sql`). First login forces a password change (see Security, below); after that, the review summary shows the manager rating alongside a "Published calibrated score" card once HR has run the employee through calibration and published the result — the seed data ships with Dara already calibrated (`3.580` → `3.200`, moderated down a band) and published, so this renders on first login rather than needing manual setup.

Every employee with a `draft`/`submitted` goal plan sees an "Edit my goals" link, leading to `/goals/[planId]` — build KRA categories and goals, weight them (the UI enforces the same "categories sum to 100, each category's goals sum to 100" rule the database's `validate_goal_plan_weights` enforces, computed in integer hundredths so it can't disagree with Postgres's `numeric(6,2)` over floating-point rounding), self-rate, and submit for manager review. A blank rating means "not yet assessed" — `0` is a real score and is never confused with "unrated." Submitting persists every change, computes the self rollup (`compute_goal_plan_rating`), and only then flips the plan to `submitted`, in that order — flipping status first and hoping the rollup call succeeds afterward would risk stranding a plan in a state nobody could recover without going around the UI. Anyone who is a `line_manager` participant on at least one plan sees a "My reports" link to `/reports` — a list of the plans they can act on, each labeled with whether it's actually open for rating right now (a plan has to be `submitted`, not just `draft`, for the manager to touch it — rating an unsubmitted plan is blocked at the database level, not just hidden in the UI). `/reports/[planId]` shows the employee's self-assessment read-only alongside editable manager fields, and "Mark as reviewed" follows the identical rollup-then-status-flip ordering as the employee's submit action.

HR admins (`hr.admin@example.com` / `password123`) also see a "Calibration" link in the header, leading to `/calibration` — the facilitator board. Sessions render as a Kanban of the session's configured bands; every score change goes through an "Adjust" modal (the database only accepts an exact `calibrated_score`, never a band directly, so there's no such thing as a silent commit) with a live preview of which band that score lands in. Dragging a card onto a different band column is a convenience on top of the same modal — it pre-fills a sensible score inside the target band's range and still requires an explicit Save, so a fumbled drag on a touchscreen can't quietly mis-rate someone. Drag runs on one Pointer Events controller (mouse, touch, and pen share the same code path) rather than the HTML5 Drag and Drop API, which never fires on touch at all — each card has a dedicated `touch-action: none` grip handle so a genuine drag never fights the board's own horizontal scroll or the page's vertical scroll, and the board auto-scrolls horizontally when a drag nears either edge, since only about one band column fits on a phone screen at a time. Finalizing a session (behind a confirmation dialog — there's no un-finalize) freezes further adjustment and unblocks publishing, per-plan, from the board.

HR admins also see a "Manage review cycles" link, leading to `/review-cycles` — a list of every cycle regardless of status, a create form, and one "advance to \<next status\>" button per cycle (never a free-form status picker — the UI only ever offers the single legal next step, matching what the database enforces). Every authenticated user sees "My objectives", leading to `/objectives` — their own OKR tree, a create form scoped to cycles they're actually a participant in, and `/objectives/[objectiveId]` for adding key results and recording check-ins. Progress is never edited as a number: a key result's `current_value` only ever changes by recording a check-in, and the UI re-reads the recomputed value and score from the database afterward rather than computing either client-side, so what's on screen always has a database-verified event behind it. The check-in history list is append-only and shows who recorded each entry and when.

**Design system:** Data-Dense Dashboard pattern, navy/blue B2B palette (`#0F172A` ink, `#0369A1` accent — WCAG AA/AAA verified in both light and dark), Lexend (headings) + Source Sans 3 (body) + IBM Plex Mono (tabular score data), Phosphor icons. OKR key-result scores use the Viva Goals 0.0–0.4/0.5–0.6/0.7–0.9/1.0 red-amber-green-orange banding convention from the original research.

**Device-agnostic:** verified at 375px (mobile), 768px (tablet), and desktop widths, plus light/dark `prefers-color-scheme`. All interactive controls (inputs, buttons, the password-visibility toggle) hit a 44×44px minimum touch target. Mobile text inputs are 16px to avoid iOS auto-zoom on focus. Every route has a friendly `error.tsx` and `not-found.tsx` — no framework default error pages.

## Security

- **RLS is the primary boundary**, not the frontend — every table is covered (see `scripts/verify.sql`), and policies key off explicit participant/grant rows, never a bare role name. A logged-in user can only ever see what their `review_participant` rows entitle them to, regardless of what the UI shows or hides.
- **Forced password rotation.** HR-provisioned accounts have no password of their own (`profiles.password_changed_at` starts `NULL`), so first login redirects to `/change-password` before anything else is reachable. Passwords expire again after 60 days (`lib/password.ts`'s `PASSWORD_ROTATION_DAYS`), enforced server-side on every load of `/review`, not just client-side.
- **Password policy**: minimum 10 characters, upper + lower + digit + symbol, enforced both client-side (live checklist, immediate feedback) and server-side (`supabase/config.toml`'s `password_requirements` — GoTrue rejects non-compliant passwords on the actual `updateUser` call, so the client check is a UX convenience, not the real gate). Seeded demo passwords (`password123`) are exempt because they're inserted directly as pre-hashed rows, not through this API — that's what makes the forced-first-login-change flow possible to demo at all.
- **Self-service is column-scoped, not just row-scoped.** A user can update their own `profiles` row (needed to record their own password change), but a `BEFORE UPDATE` trigger blocks them from touching anything on that row except `password_changed_at` — name, email, manager, and HR-admin flag stay HR-only, mirroring the same column-level-guard pattern used for line-manager goal ratings in Phase 1.
- **No user enumeration**: the login error message is identical whether the email doesn't exist or the password is wrong.
- **Security headers** (`web/next.config.ts`): `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, and HSTS. No CSP yet — deliberately deferred rather than shipping a guessed-at policy that might silently break Turbopack's dev-mode HMR; that's the clear next step before a production deploy.
- **Auth rate limiting** is GoTrue's built-in `[auth.rate_limit]` config in `supabase/config.toml` (30 sign-in attempts / 5 min / IP by default) — not reimplemented at the app layer.
- **Known follow-up**: `web/middleware.ts` uses Next.js's now-deprecated `middleware` convention (Next recommends renaming to `proxy.ts`). Left as-is rather than blind-applying an unverified codemod to security-critical session-refresh code — functionally correct, just not on the newest convention name.
- **Known follow-up**: HR's RLS grant on `calibration_session`/`calibration_band` is a blanket `is_hr_admin()` policy, so nothing at the database level stops a direct API call from reopening a finalized session or deleting a band out from under a participant (`band_id` uses `ON DELETE SET NULL`). The facilitator UI doesn't expose an un-finalize or band-delete control, so this isn't reachable through normal use of what's shipped — a deliberate scope boundary for now, not an oversight, and the next thing to harden if this UI's write surface grows.

- **Phase 1 (done):** KRA goal plans, categories, weighted goals, cascade/align, the Average Method rollup, RLS.
- **Phase 2 (done):** Objective/Key-Result tree, check-ins, OKR alignment, matrix-manager role with scoped ratings, combined KRA+OKR review summary.
- **Phase 3 (done):** Calibration sessions with configurable bands (no hardcoded box count), the publish/close gate, an HR-only comp export surface, and a facilitator UI (Kanban board, Adjust-modal-as-commit-primitive with drag as convenience, session creation, finalize/publish) — including a correctness fix found while building it: a published plan can no longer be silently recalibrated by adding it to a second, still-open session.
- **Frontend (done):** employee review summary page, the goal/rating creation workflow (employee editor + manager rating view), the HR-only calibration facilitator board, review-cycle management, and OKR/check-in creation (Next.js + Tailwind + Supabase Auth/SSR).

**Gap-closure effort (in progress):** a brutal audit of this repo found that, despite the schema/RLS/calibration work above being solid, the core "set a goal, self-assess, get rated" loop had **no UI at all** — every rating in the seed data was hand-written SQL, and several other real gaps (no review-cycle management, no OKR creation, no pagination, zero automated frontend tests, no deploy pipeline, and more) existed alongside it. That's being worked through round by round, each round going through the same brief → independent-plan → cross-challenge → ruling → build → adversarial-review → live-verify cycle as every phase above:
  - **Round 1 (done): the Goal/Rating creation UI** — described in the Frontend section above. Also closed two real security gaps the review process found beyond the original brief: an employee could previously write `goal.manager_rating` directly (both via UPDATE and, worse, via INSERT on a brand-new goal), and a manager could rate a goal before the employee had even submitted it. See "Design decisions," above.
  - **Round 2 (done): review-cycle management + OKR/check-in creation UI** — described in the Frontend section above. The independent-plan cross-challenge round surfaced four real gaps beyond the original brief that both builders converged on fixing: `review_cycle.status` had no lifecycle guard at all (any HR call could skip stages or reopen a closed cycle), a closed cycle didn't actually freeze OKR writes at the database level, a key-result owner could forge `current_value`/`score_override` directly instead of going through a check-in, and HR's blanket policy on `check_in` allowed silently rewriting or deleting check-in history. My own live-verification pass on top of that found a fifth, older bug neither builder's new code was responsible for: a latent Phase 2 self-referencing-RLS issue in `can_read_objective()` that made every non-HR "create an objective, read it back" request fail, invisible until this round because nothing had ever exercised that exact path before. See "Design decisions," above, for all five.
  - **Rounds 3–9 (not started):** admin UI (employee onboarding, goal cascade/alignment, matrix-manager scope grants); the comp-export frontend surface + pagination; calibration un-finalize/unpublish + tightening the blanket HR RLS grant on `calibration_session`/`calibration_band`; password reset + past-cycle visibility; CSP + the `middleware.ts`→`proxy.ts` migration; an automated frontend test framework; a generic audit-log table. Explicitly **not** in scope, by the user's own call when this effort started: real email/webhook notifications (no provider account exists to wire up), and any actual hosted deployment (this stays a local-only, GitHub-pushed project) — both are documented here rather than silently dropped.
