# okr-kra-pms

A proof-of-concept schema for a web-based performance management system covering both **KRA** (Key Result Area) scorecards and **OKR** (Objectives & Key Results) tracking — the two frameworks most mid-size orgs run in parallel, and the two most performance-management tools (SAP SuccessFactors, Oracle Fusion HCM, Workday, Lattice, Betterworks) keep structurally separate rather than merging into one score.

This repo is schema-first: Postgres migrations + Row-Level Security policies for a Supabase backend, built and cross-verified by two independent AI coding agents (Jcode/Claude and Codex/GPT-5.6) with an adversarial cross-challenge round before anything merges, and a live `supabase db reset` + RLS/rollup verification pass before anything ships. See `VERIFICATION.md` for the actual test queries and expected results.

## Design decisions

- **KRA drives the appraisal number, OKR is a strategic overlay.** KRA goals roll up into one weighted rating (Oracle's "Average Method"); OKR key results carry their own 0.0–1.0 score and feed evidence into the same review without being mathematically merged into the KRA rating.
- **Cascade and align are different relationships**, not one generic parent-goal pointer — a cascade copies a manager's goal down to a report; an alignment links two independently pre-existing goals, one link up per goal, many down.
- **Matrix management is a first-class, explicitly-scoped role** — a matrix manager can rate only the specific KRA categories they've been granted, keyed off an explicit grant row, never off the role name alone.
- **Every RLS policy is keyed off an explicit participant/grant table** (`review_participant`, `review_participant_scope`), never off a bare role name or job title — this was a deliberate response to a documented SAP SuccessFactors permissioning quirk where a broadly-granted role surfaced UI for people it shouldn't have applied to.
- **Calibration is a human-facilitated override, never an algorithm.** Every vendor researched (SAP, Workday, Lattice, Betterworks) explicitly avoids forced-distribution normalization — `calibration_participant` stores the pre-calibration snapshot (`original_score`, immutable) alongside the HR-adjusted value (`calibrated_score`) as the audit trail, and nothing auto-curves anyone's rating.
- **The employee never sees a calibrated/final score until HR explicitly publishes it** (`employee_goal_plan.published_at`) — even mid-calibration, even after the manager's raw rating is already visible. Publishing itself is blocked while the plan's calibration session is still open, so a published score can never be a stale, un-finalized number.
- **Comp export is deliberately more restricted than day-to-day review visibility.** A line manager can already see their own reports' individual reviews, but `comp_export_rows` gates on `is_hr_admin` explicitly — compensation-cycle data gets a narrower circle than performance-review data, as a deliberate governance boundary, not an oversight.
- **A published score is a one-way door.** Building the facilitator UI surfaced a real hole in the original Phase 3 functions: nothing stopped a published plan from being added to a *second*, still-open calibration session, silently changing the employee's already-visible published score without a new publish action. `add_plan_to_calibration_session` now rejects that outright (`published_at is not null` → `55000`), and `calibration_eligible_plans` excludes published plans from the picker so HR never sees the option in the first place.
- **RLS row-visibility and column-write scope are two different guarantees, and only one of them existed for the goal-rating workflow before this round.** `goal_participant_update`'s `WITH CHECK` had always tested "can this caller reach this row," never "which columns did they change" — so an employee who could legitimately edit their own goal could also silently write `manager_rating`/`manager_comment` directly, and could insert a brand-new goal pre-populated with a fake manager rating (the INSERT policy checked category ownership only, not column contents). Both are closed now: a mirrored `restrict_employee_goal_updates()` trigger column-scopes the employee's UPDATE path exactly like the pre-existing manager trigger already did, and `goal_employee_insert`'s `WITH CHECK` now requires `manager_rating`/`manager_comment` to be `null` at creation time. `can_manager_rate_goal` was also tightened to require the specific plan's status be `submitted`, not just "the review cycle is somewhere in its manager_eval window" — a manager could previously rate a goal on a plan the employee hadn't submitted yet, or keep changing ratings after the plan was already `manager_reviewed`.
- **A review cycle's status is a one-way lifecycle, not a free-form field.** Before Round 2, `review_cycle_hr_all`'s blanket `for all` grant meant HR could set `status` to any value in any order via a raw API call — skip straight to `closed`, or reopen a closed cycle — with nothing in the database to stop it. `restrict_review_cycle_status_transition()` now enforces the exact `draft → active → self_eval → manager_eval → closed` sequence, one step at a time, for every caller including HR, raising `55000` (not `42501` — this is an invalid-state error, not a permission error, and the two are kept distinguishable end to end). New cycles must be inserted as `draft`. Once `closed`, a cycle is frozen for good: objective/key-result/check-in writes against a closed cycle are rejected at the trigger level too, including for HR, so "closed" actually means closed rather than just hidden by the UI.
- **OKR progress has exactly one legitimate writer: the check-in trigger.** Before Round 2, an objective owner could `UPDATE key_result SET current_value = ...` directly, bypassing the check-in history entirely — the score would look real but have no event behind it. `restrict_key_result_owner_updates()` now blocks direct `current_value`/`score` writes from anyone, including HR (HR still sets `score_override` for a manual override, which is a different, explicit column). The guard distinguishes a direct client UPDATE from the check-in trigger's own legitimate propagation UPDATE via `pg_trigger_depth()` (depth 1 for a direct call, depth 2 when the write originates from inside `apply_check_in_to_key_result`'s own AFTER INSERT trigger) — a regression test in `verify.sql` pins both sides of that distinction so a future change to either trigger can't silently break the other. `check_in` itself is now append-only end to end: `checked_in_by`/`created_at` are force-set server-side regardless of what a client sends, and the previous blanket HR policy (which allowed HR to silently edit or delete check-in history) is replaced with HR read-only — check-ins are the evidence trail behind OKR progress, and a record that can be quietly rewritten after the fact isn't a record.
- **A self-referencing RLS `SELECT` policy can fail against the very row it just inserted.** Building the objective-creation UI surfaced a latent bug that had existed since Phase 2 and was simply never exercised: `can_read_objective()`'s "am I the owner" branch re-queries `objective` by id, and when that function is invoked as part of the `SELECT`-policy check Postgres performs for `INSERT ... RETURNING` (what `.insert().select()` issues), the self-referencing subquery runs under a snapshot taken at the start of that same statement — before the row it's looking for exists. A plain `INSERT` without `RETURNING`, or a separate follow-up `SELECT`, both work fine; only the same-statement create-and-read-back path was broken, which is exactly the shape every insert-returning-the-new-row UI action uses. Fixed in `0019` by checking `owner_id = auth.uid()` directly in the `USING` clause — a `USING` clause has direct access to the row's own columns and needs no subquery for the self-owned case — before falling back to `can_read_objective()` for the manager/matrix-manager cases, which read an already-committed parent row and aren't snapshot-fragile. `key_result`'s and `check_in`'s `SELECT` policies were checked for the same pattern and don't have it — both key off their *parent* row's id, which already exists under any snapshot, not their own.
- **The same self-referencing-RLS-under-`RETURNING` bug also existed on `goal`, since Phase 1** — same root cause as the `objective` case above, in `can_read_goal()`'s `is_goal_participant()` branch, and same fix shape in `0021`: a direct, non-self-referencing "do I own the plan this goal's category belongs to" check added to `goal_select_scoped`'s `USING` clause, ahead of the self-referencing fallback. This one had gone unnoticed for even longer than the `objective` case — Round 1's goal editor was live-tested extensively, but only against *updating* pre-existing seed goals; nothing exercised a plain employee `goal` insert-and-read-back until Round 3's "Add goal" button, live-verified during this round, hit it. `kra_category`'s equivalent insert path was checked for the same pattern and is safe — its participant check queries `review_participant` only, never `kra_category` itself.
- **A self-referencing Postgres foreign key needs an explicit, correctly-directed embed hint, and the wrong hint fails silently, not loudly.** The admin employee list joins `profiles` to itself (`manager_id → profiles.id`) to show each employee's manager's name. The initial query used PostgREST's `table!column` embed hint (`manager:profiles!manager_id(full_name)`) — the pattern used everywhere else in this codebase for embeds — but for a table referencing *itself*, that hint resolves as the reverse, one-to-many direction (an employee's direct reports) instead of the intended many-to-one direction (the employee's own manager). It doesn't error; it just returns the wrong, differently-shaped data, which happened to render a *plausible-looking but wrong* manager name for every seeded employee (the query returns each employee's reports, and the code takes the first one — for the original seed data, that first report's name happened to read as a believable "manager"). It only became visibly wrong once Round 3's live verification added an employee with no reports of her own, whose "manager" then rendered as blank. Fixed by using the plain column-name embed (`manager:manager_id(full_name)`, no table prefix, no `!` hint) instead — for a self-referencing FK, the bare column form is the one PostgREST resolves unambiguously in the forward (many-to-one) direction. Confirmed directly against the REST API before and after the fix, not just by reasoning about it.
- **A paginated list and the option set a form built from that same data are two different queries, not one.** Pagination landed across the admin employee directory, the matrix-scope grants list, `/objectives`, `/reports`, and `/calibration`'s session list — but wherever a paginated list's rows also double as a picker's candidates (the "assign a manager" `<select>` on `/admin`, the plan/matrix-manager pickers on `/admin/matrix-scopes`), the picker is fetched as a second, deliberately unbounded query. Silently omitting a valid manager because they happen to sort onto a different directory page would be a data-entry bug, not a UX rough edge — you'd assign the wrong manager, or conclude the right one doesn't exist. `/review-cycles` was deliberately left unpaginated: a review cycle is created a handful of times a year, this list will realistically never reach a second page of 25, and HR benefits from seeing the full chronology in one view — pagination was added where a list can genuinely grow unbounded, not everywhere a list exists.
- **`comp_export_rows`'s core business rule — which score wins when both a manager rating and a calibrated score exist — had never actually been pinned by a test**, despite the function's whole purpose being to expose exactly that precedence to HR. Round 4's expanded `verify.sql` coverage cross-validates the function's output against the underlying `employee_goal_plan`/`goal_plan_rating`/`calibration_participant` rows directly (not hardcoded expected constants) for both the calibrated-overrides-manager case and the manager-only-fallback case, plus the `manager_full_name`/`band_label` null paths a manager-less or uncalibrated employee produces — none of which had prior coverage.
- **"Un-finalize a calibration session" was closing a live vulnerability, not a hypothetical one.** `calibration_session`/`calibration_band` had blanket `for all using (is_hr_admin())` RLS policies with no state-transition guard — meaning, before this round, any HR-authenticated caller could issue a raw `UPDATE calibration_session SET status = 'open'` directly against PostgREST, and nothing rejected it. Because `adjust_calibration_participant`'s only defense against editing a `calibrated_score` was a function-level `if status = 'finalized' then reject` check (not a trigger), reopening a finalized session that way and then calling `adjust_calibration_participant` on an *already-published* participant would silently change a score the employee had already seen — completely undermining the "published score is a one-way door" guarantee above. That's now closed at three layers: the blanket `for all` policies are gone entirely (direct `INSERT`/`UPDATE`/`DELETE` grants on both tables are revoked from `authenticated` — confirmed safe to remove since no UI path ever wrote to them directly; session/band creation isn't exposed in the app today either, before or after this change), a `before insert or update` trigger on `calibration_session` rejects `finalized → open` outright, and the one sanctioned path through it (`unfinalize_calibration_session`) authorizes itself to the trigger via a one-time random token recorded in a `private` schema table that's revoked from every API role including `service_role` — a bare session GUC would have been guessable/forgeable by a client setting the same setting name itself, so the token is matched and consumed (deleted) inside the trigger, not just checked for presence.
- **Unpublishing a plan and un-finalizing its session are two different, independently-gated actions, not one "undo" button.** `unpublish_employee_goal_plan(plan_id, reason)` only clears `published_at` — `calibrated_score`, `band_id`, and the session's status are untouched, and the plan can be re-published immediately while the session stays finalized. `unfinalize_calibration_session(session_id, reason)` is hard-blocked (`55000`) while *any* participant in that session is still published. The dependency only runs one direction (unpublish doesn't require unfinalizing first; unfinalizing requires everything already unpublished) because forcing the coarser action to always precede the finer one would mean fixing one employee's mistaken publish by reopening scoring for everyone else in the session too. Un-finalizing returns a session to a plain `'open'` state — no third enum value, no behavioral branch added to `adjust_calibration_participant` — because the real safety property was never "can't re-score after reopening," it's "can't re-score anything already published," which the zero-published precondition guarantees on its own; `adjust_calibration_participant` additionally checks this directly now too, as a second, independent line of defense. Both actions require a non-blank reason, recorded as the *latest* reversal on the affected row (`last_unfinalized_at/by/reason`, `last_unpublished_at/by/reason`) — a snapshot, not a log, since the generic audit-log table is a later round's scope; a repeated reversal overwrites it rather than pretending to be history it isn't.
- **Password recovery reuses Supabase Auth's own PKCE flow rather than inventing a token scheme**, and the login page's "identical response either way" principle extends to it: `/forgot-password` shows the same confirmation message whether or not the address exists, so an attacker can't use it to enumerate accounts. `/reset-password` waits for the recovery session Supabase's client SDK establishes from the emailed link before enabling the form, shows a distinct error state for a missing/expired/already-used link rather than a blank screen, and — since a reset is also the account's forced-rotation moment — reuses `web/lib/password.ts`'s policy check verbatim and stamps `profiles.password_changed_at` on success, so a recovered account isn't immediately routed back through forced rotation again. Production email delivery needs a real SMTP provider configured (`[auth.email.smtp]` in `supabase/config.toml` is deliberately left commented out, matching this project's standing "no external provider" scope) — locally, the flow is fully real and fully testable via the Supabase CLI's bundled local mail catcher on port `15424`, with nothing simulated.
- **`site_url`/`additional_redirect_urls` matching is exact-string, not host-equivalence** — live-testing the reset flow through an actual browser (not just a direct API call) surfaced a real bug: `supabase/config.toml`'s redirect allow-list only listed `127.0.0.1` variants, but this repo's own dev workflow — every prior round's browser testing, `npm run dev`'s printed URL — uses `http://localhost:3000`. GoTrue does not treat `localhost` and `127.0.0.1` as the same origin for its exact-match allow-list, so the emailed reset link's `redirect_to` silently fell back to the bare `site_url` instead of `/reset-password`, landing a real user back at the homepage with their recovery token discarded rather than on the form that could use it. Fixed by adding explicit `localhost` counterparts alongside the existing `127.0.0.1` entries. A raw API-level check of the `/recover` response would never have caught this — it only surfaces by actually clicking the real emailed link in a browser navigated to the app's real dev URL.
- **Past review-cycle visibility needed almost no new backend** — `loadReviewCycles` was already correctly RLS-scoped (HR sees every cycle, an employee sees only cycles they actually participated in, via the existing `review_cycle_select_scoped` policy) and `employee_review_summary(p_review_cycle_id, p_employee_id)` never had a hardcoded "current cycle" assumption in its body. The entire gap was that `/review` only ever asked for the single newest-started cycle; adding a `?cycle=` picker that validates the requested id against the caller's own RLS-scoped cycle list (falling back to the default rather than erroring on an id the caller can't read) was the whole fix. Building this also surfaced two smaller pre-existing bugs on `/review` itself: "Edit my goals" was gated on plan status alone, so it could offer an edit link into a closed cycle that the database was guaranteed to reject; and the summary RPC was read with `.single()`, which turns the perfectly normal "no plan in this cycle" case (zero rows) into a client-side error rather than an empty state. Both fixed in passing.
- **A schema change silently broke three unrelated frontend features for three months, and nothing detected it.** Round 5's `0022_calibration_reversal_controls.sql` added `employee_goal_plan.last_unpublished_by`, a second foreign key to `profiles` alongside the existing `employee_id` one. From that point on, every bare `profiles(...)` embed reaching through `employee_goal_plan` became ambiguous — PostgREST can no longer guess which relationship you mean and rejects the whole query with `PGRST201` — and every one of this codebase's `const { data } = await supabase...` read helpers discards the error silently, so the ambiguity presented as an empty result, not a crash: `/admin/matrix-scopes`'s "whose plan" picker showed no plans (and any existing grant's category name fell back to "a section you can no longer see"), `/reports` showed zero direct reports to every manager in the app, and both `LINKABLE_GOAL_SELECT`-backed pickers ("Cascade a goal to me," "Align an existing goal") offered nothing to link. None of this tripped `npm run lint`, `npm run build`, or `scripts/verify.sql` — it's an RLS-independent PostgREST embed-resolution error, invisible to every check this project runs except actually clicking through the app as each role and noticing a list that should have rows doesn't. Found during a brutal-QA pass that abused every button and form as three different seeded users rather than just confirming pages load; reproduced first via a direct REST call against each broken query (`curl` with the service-role key) to isolate the exact `PGRST201` before touching any code, then fixed at all three call sites using this codebase's existing self-referencing-embed convention (`profiles:employee_id(...)`, the same bare-column form `manager:manager_id` already used for `profiles`'s actual self-reference) rather than the `!constraint_name` hint form. Confirmed broken and then fixed via the same direct-REST method before touching the UI, then re-verified live as HR, as a manager, and as an employee. This is the same root-cause *shape* as the self-referencing-RLS-under-`RETURNING` bug class from Rounds 2–3 — a correctness property that held under the schema present when a query was first written silently stopped holding once a later, unrelated migration changed that schema — but manifests as a PostgREST embed-planning error rather than an RLS snapshot issue.
- **A strict CSP needs a per-request nonce, and a per-request nonce needs `proxy.ts`, not `next.config.ts`.** The five pre-existing static security headers work as a fixed table because none of them vary by request; `Content-Security-Policy`'s `script-src` can't, once it carries a nonce, so it moved to `proxy.ts` alone rather than duplicating the header in both places and hoping the layering resolves the way you'd expect. The policy: `script-src` is nonce + `'strict-dynamic'` with no `'unsafe-inline'` in production (`'unsafe-eval'` only under `NODE_ENV==='development'`, for React's dev-mode diagnostics) — genuinely strict, since a repo-wide grep found zero `dangerouslySetInnerHTML`, inline `<script>`, or `eval` anywhere in application code. `style-src 'self' 'unsafe-inline'` is the one deliberate, stated exception: 46 files style through React's `style={{...}}` prop reading this project's CSS custom properties, a nonce doesn't cover `style=` attributes at all (that's the separate `style-src-attr` directive, which just falls back to `style-src` when omitted), and rewriting that pattern app-wide is a real, separate effort explicitly out of scope for adding a CSP. `connect-src` derives the Supabase origin from `NEXT_PUBLIC_SUPABASE_URL` once at module load (the value can't change within a running server process, so re-parsing it per request is pure overhead) rather than hardcoding the local dev origin. `base-uri 'none'` and `img-src 'self'` are both stricter than they need to be defensively — the app has no `<base>` tag anywhere and renders no images at all beyond local SVGs, so there's nothing to weaken them for.
- **Next's own client bundle needed the fallback it was built to need, not a hypothetical one.** `'strict-dynamic'` requires forcing every route to dynamic rendering, and the brief's honest framing was "verify this empirically, don't assume every route already qualifies because it happens to read a Supabase cookie." It didn't: before this round, six routes were static (`/`, `/login`, `/change-password`, `/forgot-password`, `/reset-password`, `/_not-found`) — none of them touch a cookie-scoped Supabase call along their render path, and a static build of `/login` genuinely had zero `nonce=` attributes on any script tag, which would have silently broken chunk loading in a real browser despite `next build` succeeding. `await connection()` in the root layout forces the whole app dynamic; the before/after route table (six static, now zero) is the actual evidence this was necessary, not an assumption baked into the ruling ahead of time.
- **The one hazard both independent builders found in the exact same place, unprompted, is the one worth trusting most.** Supabase's SSR `setAll` cookie callback in `proxy.ts` reassigns `response` mid-request when a session token needs refreshing; if that reassignment rebuilds the response from the original, un-nonced `request` object, the CSP nonce silently disappears from that response only — a failure `npm run lint`/`npm run build` cannot see, since it's a runtime data-flow issue, not a type or syntax one, and it would only ever surface as a broken script tag in a real user's browser on whichever request happened to trigger a token refresh. Both plans converged independently on the identical fix (clone `request.headers` once, thread that single object into *every* `NextResponse.next()` call including the one inside `setAll`) before either builder had seen the other's plan, which is stronger evidence of correctness than either plan alone. The adversarial review traced the actual control flow by hand rather than trusting the diff compiles — the one gap even that couldn't close is that no seeded account in this local environment ever has a live-enough session to trigger a real token refresh mid-request (every seeded password is expired at first login, redirecting to `/change-password` before `getUser()` needs to refresh anything), so the fix is verified correct by construction and by hand-trace, not by an end-to-end reproduction of the exact refresh path — the honest limit of what local seed data can exercise.
- **A grant with no way to revoke it is a bug, not a scope boundary** — unlike goal cascade/alignment links, which the Frontend section documents as *deliberately* permanent with no unlink screen, `/admin/matrix-scopes`'s access grants have no such stated rationale anywhere; HR could create them but never remove one, including a grant that had gone stale because the plan or category it pointed at no longer resolved. Added `revokeMatrixScopeAction` (Server Action, re-verifies HR the same way every other admin action does) and a two-click revoke control per grant — no modal, since the action is trivially reversible by re-granting from the form immediately above it, unlike the calibration reversals' typed-confirmation friction, which exists specifically because *those* actions touch a score an employee may have already seen.

```

```

The same script gates every push in CI (`.github/workflows/ci.yml`).

## Frontend

`web/` is a Next.js (App Router) + Tailwind v4 app. The employee review summary (`/review`) is the landing screen — KRA scorecard and OKR objectives/key results side by side, backed by the `employee_review_summary` RPC and enforced end-to-end by the RLS policies above (log in as a different seeded user and you see a different, correctly-scoped result).

```bash
cd web
npm install
cp .env.example .env.local   # local defaults already match `npx supabase status`; swap in real project keys outside local dev
npm run dev
```

`.env.example` ships three vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and — since Round 3 — `SUPABASE_SERVICE_ROLE_KEY`. That last one is server-only (never `NEXT_PUBLIC_*`), used exclusively by the employee-provisioning Server Action to call the Supabase Auth Admin API; see Security, below, for how it's isolated from the rest of the app.

Local seed credentials: `dara.sok@example.com` / `password123` (or any other seeded user — see `supabase/seed.sql`). First login forces a password change (see Security, below); after that, the review summary shows the manager rating alongside a "Published calibrated score" card once HR has run the employee through calibration and published the result — the seed data ships with Dara already calibrated (`3.580` → `3.200`, moderated down a band) and published, so this renders on first login rather than needing manual setup.

Every employee with a `draft`/`submitted` goal plan sees an "Edit my goals" link, leading to `/goals/[planId]` — build KRA categories and goals, weight them (the UI enforces the same "categories sum to 100, each category's goals sum to 100" rule the database's `validate_goal_plan_weights` enforces, computed in integer hundredths so it can't disagree with Postgres's `numeric(6,2)` over floating-point rounding), self-rate, and submit for manager review. A blank rating means "not yet assessed" — `0` is a real score and is never confused with "unrated." Submitting persists every change, computes the self rollup (`compute_goal_plan_rating`), and only then flips the plan to `submitted`, in that order — flipping status first and hoping the rollup call succeeds afterward would risk stranding a plan in a state nobody could recover without going around the UI. Anyone who is a `line_manager` participant on at least one plan sees a "My reports" link to `/reports` — a list of the plans they can act on, each labeled with whether it's actually open for rating right now (a plan has to be `submitted`, not just `draft`, for the manager to touch it — rating an unsubmitted plan is blocked at the database level, not just hidden in the UI). `/reports/[planId]` shows the employee's self-assessment read-only alongside editable manager fields, and "Mark as reviewed" follows the identical rollup-then-status-flip ordering as the employee's submit action.

HR admins (`hr.admin@example.com` / `password123`) also see a "Calibration" link in the header, leading to `/calibration` — the facilitator board. Sessions render as a Kanban of the session's configured bands; every score change goes through an "Adjust" modal (the database only accepts an exact `calibrated_score`, never a band directly, so there's no such thing as a silent commit) with a live preview of which band that score lands in. Dragging a card onto a different band column is a convenience on top of the same modal — it pre-fills a sensible score inside the target band's range and still requires an explicit Save, so a fumbled drag on a touchscreen can't quietly mis-rate someone. Drag runs on one Pointer Events controller (mouse, touch, and pen share the same code path) rather than the HTML5 Drag and Drop API, which never fires on touch at all — each card has a dedicated `touch-action: none` grip handle so a genuine drag never fights the board's own horizontal scroll or the page's vertical scroll, and the board auto-scrolls horizontally when a drag nears either edge, since only about one band column fits on a phone screen at a time. Finalizing a session (behind a confirmation dialog) freezes further adjustment and unblocks publishing, per-plan, from the board. Finalizing is reversible now: a finalized session shows an "Un-finalize session" control, visibly disabled with an explanation naming the blocking count when any participant is still published, and requiring a reason plus typing `UNFINALIZE` to confirm once it's actually available — this is the more consequential of the two reversal actions, so it carries more confirmation friction than either Finalize or Publish. Each published participant separately gets an "Unpublish" action in place of the (already-used) Publish button — narrower, one-employee-at-a-time, reason required but no typed confirmation, since the score and band underneath are untouched, only visibility.

HR admins also see a "Manage review cycles" link, leading to `/review-cycles` — a list of every cycle regardless of status, a create form, and one "advance to \<next status\>" button per cycle (never a free-form status picker — the UI only ever offers the single legal next step, matching what the database enforces). Every authenticated user sees "My objectives", leading to `/objectives` — their own OKR tree, a create form scoped to cycles they're actually a participant in, and `/objectives/[objectiveId]` for adding key results and recording check-ins. Progress is never edited as a number: a key result's `current_value` only ever changes by recording a check-in, and the UI re-reads the recomputed value and score from the database afterward rather than computing either client-side, so what's on screen always has a database-verified event behind it. The check-in history list is append-only and shows who recorded each entry and when.

HR admins also see an "Admin" link, leading to `/admin` — the employee directory, with a create-account form and a per-employee edit form (manager, HR-admin flag). Creating an employee is the only write path in this app that goes through the Supabase Auth Admin API rather than a plain RLS-governed insert: it creates the sign-in account and the `profiles` row together, in a Server Action that re-verifies the caller is HR *before* it ever touches the service-role key, and returns a one-time temporary password for HR to hand off directly (no email is sent — that's out of scope, same as every other notification path in this project). `/admin/matrix-scopes` is the guided flow for granting matrix-manager rights: pick a plan, pick who gets access, pick which KRA categories and/or objectives on that plan they can rate — the underlying `review_participant` row is created automatically the first time someone is granted a scope, with no separate step to remember. Each existing grant carries a revoke control (two clicks, no modal — unlike the cascade/align links below, a scope grant is trivially re-grantable, so it doesn't need the same permanence). Every goal in `/goals/[planId]` can be linked to a parent goal two ways: "Cascade a goal to me" copies one of your manager's goals into your own plan as a brand-new goal (title, description, target, and scale copied; weight prefilled but yours to set) via a single atomic database function, so a failed link can never strand a half-created goal; "Align an existing goal" links one of your own already-existing goals upward to any readable parent without copying anything. Both link types are permanent once created — the UI says so plainly, since only HR can unlink them, and there's currently no unlink screen. `/objectives/[objectiveId]` gets the equivalent alignment control for OKRs.

`/admin/comp-export` (linked from `/admin`) is HR's compensation-cycle export: pick a review cycle, see every published plan's final score (calibrated score if one exists, manager rating otherwise — the same precedence `comp_export_rows` has always computed) and calibration band in a 25-row-paged table, and download the complete cycle as CSV regardless of what page the table happens to be showing — the download re-fetches in bounded batches rather than trusting whatever's already on screen, so a 1500-row cycle exports all 1500 rows, not the visible 25. The CSV escapes every field defensively against spreadsheet-formula injection (a leading `=`/`+`/`-`/`@` gets a neutralizing prefix, matching the OWASP CSV-injection guidance) — a compensation export is exactly the kind of file that gets opened straight into Excel by someone who won't think to check. The admin employee directory, the matrix-scope grants list, `/objectives`, `/reports`, and `/calibration`'s session list are all paginated the same way (25 rows, `?page=N`, previous/next); `/review-cycles` deliberately isn't (see Design decisions).

Signed-out users see a "Forgot password?" link on `/login`, leading to `/forgot-password` → an emailed reset link → `/reset-password`, where the new password goes through the same policy check as everywhere else in the app. `/review` gains a "Review cycle" picker once a user has more than one cycle to look at — switching to a past, closed cycle shows a read-only note and that cycle's own self/manager ratings, computed and stored back when it was still open, not recomputed retroactively.

**Design system:** Data-Dense Dashboard pattern, navy/blue B2B palette (`#0F172A` ink, `#0369A1` accent — WCAG AA/AAA verified in both light and dark), Lexend (headings) + Source Sans 3 (body) + IBM Plex Mono (tabular score data), Phosphor icons. OKR key-result scores use the Viva Goals 0.0–0.4/0.5–0.6/0.7–0.9/1.0 red-amber-green-orange banding convention from the original research.

**Device-agnostic:** verified at 375px (mobile), 768px (tablet), and desktop widths, plus light/dark `prefers-color-scheme`. All interactive controls (inputs, buttons, the password-visibility toggle) hit a 44×44px minimum touch target. Mobile text inputs are 16px to avoid iOS auto-zoom on focus. Every route has a friendly `error.tsx` and `not-found.tsx` — no framework default error pages.

## Security

- **RLS is the primary boundary**, not the frontend — every table is covered (see `scripts/verify.sql`), and policies key off explicit participant/grant rows, never a bare role name. A logged-in user can only ever see what their `review_participant` rows entitle them to, regardless of what the UI shows or hides.
- **Forced password rotation.** HR-provisioned accounts have no password of their own (`profiles.password_changed_at` starts `NULL`), so first login redirects to `/change-password` before anything else is reachable. Passwords expire again after 60 days (`lib/password.ts`'s `PASSWORD_ROTATION_DAYS`), enforced server-side on every load of `/review`, not just client-side.
- **Password policy**: minimum 10 characters, upper + lower + digit + symbol, enforced both client-side (live checklist, immediate feedback) and server-side (`supabase/config.toml`'s `password_requirements` — GoTrue rejects non-compliant passwords on the actual `updateUser` call, so the client check is a UX convenience, not the real gate). Seeded demo passwords (`password123`) are exempt because they're inserted directly as pre-hashed rows, not through this API — that's what makes the forced-first-login-change flow possible to demo at all.
- **Self-service is column-scoped, not just row-scoped.** A user can update their own `profiles` row (needed to record their own password change), but a `BEFORE UPDATE` trigger blocks them from touching anything on that row except `password_changed_at` — name, email, manager, and HR-admin flag stay HR-only, mirroring the same column-level-guard pattern used for line-manager goal ratings in Phase 1.
- **No user enumeration**: the login error message is identical whether the email doesn't exist or the password is wrong.
- **Security headers** (`web/next.config.ts` + `web/proxy.ts`): `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, and HSTS, all static and unconditional. `Content-Security-Policy` is per-request (nonce-based `script-src` + `'strict-dynamic'`, no `'unsafe-inline'`/`'unsafe-eval'` in production) and lives in `proxy.ts` instead, since a per-request value can't be expressed in the static header table above — see "Design decisions" for the full policy and the reasoning behind each directive.
- **Auth rate limiting** is GoTrue's built-in `[auth.rate_limit]` config in `supabase/config.toml` (30 sign-in attempts / 5 min / IP by default) — not reimplemented at the app layer.
- **The service-role key never leaves one file, and that file re-checks HR status itself.** `web/lib/supabase/admin.ts` is the only place `SUPABASE_SERVICE_ROLE_KEY` is read, guarded by `import "server-only"` (a Next-provided package that turns a Client Component importing this file into a *build* error, not a runtime one). Its one exported function authenticates the caller, checks password expiry, and calls `is_hr_admin()` — all against the normal cookie-scoped client — **before** it ever constructs the privileged client, and an eslint `no-restricted-imports` rule additionally bans importing this module from anything under `web/components/`, so the boundary is enforced by `npm run lint`, not just by convention. Every admin Server Action re-runs this authorization itself rather than trusting `/admin/layout.tsx`'s redirect alone, since a Server Action can be invoked directly.
- **Resolved in Round 7**: `web/middleware.ts` used Next.js's now-deprecated `middleware` convention, flagged here as a known follow-up rather than blind-applying an unverified codemod to security-critical session-refresh code. It's migrated now — `npx @next/codemod@canary middleware-to-proxy .`'s actual output was verified line-by-line against the original file (exact matcher, exact cookie-handling closure, function renamed, nothing else touched) rather than trusted on the strength of the codemod's own description, and the migration was the vehicle for adding the CSP above, not a separate change.
- **Resolved in Round 5**: HR's RLS grant on `calibration_session`/`calibration_band` used to be a blanket `is_hr_admin()` `for all` policy, meaning nothing at the database level stopped a direct API call from reopening a finalized session or deleting a band out from under a participant — this was flagged here as a known follow-up and has since been closed. The blanket policies and `authenticated`'s direct write grants on both tables are gone; every mutation goes through a `SECURITY DEFINER` function now, and `calibration_session`'s status transitions are guarded by a trigger with no role bypass. See "Design decisions," above, for the live vulnerability this specifically closed and the un-finalize/unpublish design.

- **Phase 2 (done):** Objective/Key-Result tree, check-ins, OKR alignment, matrix-manager role with scoped ratings, combined KRA+OKR review summary.

- **Frontend (done):** employee review summary page (with past-cycle history), self-service password reset, the goal/rating creation workflow (employee editor + manager rating view), the HR-only calibration facilitator board (including un-finalize/unpublish), review-cycle management, OKR/check-in creation, the admin UI (employee provisioning, goal cascade/alignment, matrix-manager scope grants), the HR compensation-export surface, and pagination across every list view expected to grow (Next.js + Tailwind + Supabase Auth/SSR).

**Gap-closure effort (in progress):** a brutal audit of this repo found that, despite the schema/RLS/calibration work above being solid, the core "set a goal, self-assess, get rated" loop had **no UI at all** — every rating in the seed data was hand-written SQL, and several other real gaps (no review-cycle management, no OKR creation, no pagination, zero automated frontend tests, no deploy pipeline, and more) existed alongside it. That's being worked through round by round, each round going through the same brief → independent-plan → cross-challenge → ruling → build → adversarial-review → live-verify cycle as every phase above:
  - **Round 1 (done): the Goal/Rating creation UI** — described in the Frontend section above. Also closed two real security gaps the review process found beyond the original brief: an employee could previously write `goal.manager_rating` directly (both via UPDATE and, worse, via INSERT on a brand-new goal), and a manager could rate a goal before the employee had even submitted it. See "Design decisions," above.
  - **Round 2 (done): review-cycle management + OKR/check-in creation UI** — described in the Frontend section above. The independent-plan cross-challenge round surfaced four real gaps beyond the original brief that both builders converged on fixing: `review_cycle.status` had no lifecycle guard at all (any HR call could skip stages or reopen a closed cycle), a closed cycle didn't actually freeze OKR writes at the database level, a key-result owner could forge `current_value`/`score_override` directly instead of going through a check-in, and HR's blanket policy on `check_in` allowed silently rewriting or deleting check-in history. My own live-verification pass on top of that found a fifth, older bug neither builder's new code was responsible for: a latent Phase 2 self-referencing-RLS issue in `can_read_objective()` that made every non-HR "create an objective, read it back" request fail, invisible until this round because nothing had ever exercised that exact path before. See "Design decisions," above, for all five.
  - **Round 3 (done): the admin UI** — employee provisioning, goal cascade/alignment linking, matrix-manager scope grants, described in the Frontend section above. My original brief's premise for goal cascading was wrong and both builders independently caught it during planning: a manager cannot write a report's goal outside the `manager_eval` rating window, so cascading has to be employee-initiated (linking one of your own goals from a readable manager goal), not manager-initiated as originally framed — the ruling corrected this before any code was written. Building this round's UI also surfaced two more instances of the exact self-referencing-RLS-under-`RETURNING` bug class Round 2 found: one on `goal` (Phase 1, present since the very beginning, invisible until this round's "Add goal" button became the first plain employee goal insert-and-read-back ever exercised), and a related-but-distinct bug on the same admin employee list — a self-referencing PostgREST foreign-key embed hint that silently resolved in the wrong direction, rendering a plausible-looking but wrong manager name for every employee until the fix. See "Design decisions," above, for all three.
  - **Round 4 (done): the comp-export frontend surface + a pagination pass** — described in the Frontend section above. Both builders independently converged on nearly everything (route, page size, ordering, and — without either treating it as an open question — that the CSV export must always cover the complete cycle rather than whatever page the table happens to be showing, since a truncated compensation export is a genuinely dangerous artifact). The one real design call — which lists actually warrant pagination versus which are low-cardinality enough that paginating them would just be defensive theater — is captured in "Design decisions," above, along with the correctness principle that a paginated list and any picker built from the same underlying data have to be two separate queries.
  - **Round 5 (done): calibration un-finalize/unpublish + tightening the blanket HR grant on `calibration_session`/`calibration_band`** — described in the Frontend and Security sections above. This round's brief opened by naming a live, currently-exploitable vulnerability rather than a hypothetical, and both builders' independent plans converged on the same fix shape (two separate reversal functions, unpublish as the lower-level primitive, un-finalize returning to a plain `open` state with no third enum value) down to nearly identical function signatures. The one real design disagreement — whether to drop the blanket HR grant entirely (verified safe: no UI path anywhere writes to either table directly) or leave it in place and rely solely on a new trigger — was resolved in favor of removing the grant, since the brief's second, equally-real mandate was tightening the grant itself, not just patching the one exploit through it. See "Design decisions," above.
  - **Round 6 (done): password reset + past review-cycle visibility** — described in the Frontend section above. Two independently-built, effectively unrelated features that both builders' plans converged on almost completely — same routes, same no-enumeration principle for the reset flow, same `?cycle=` picker shape reusing already-correctly-RLS-scoped existing queries. The past-cycle feature needed almost no new backend, since `loadReviewCycles` and `employee_review_summary` were already built generally enough; building it did catch two small pre-existing `/review` bugs in passing (an edit link that could point into a frozen closed cycle, and `.single()` turning "no plan in this cycle" into a client error instead of an empty state). The password-reset feature is where the round's real finding was: a raw API-level test of the reset endpoint would have looked completely fine, but actually clicking the real emailed link in a browser navigated to this repo's own documented dev URL (`localhost`, not `127.0.0.1`) surfaced a redirect-allow-list exact-match gap that would have silently discarded every real user's recovery token. See "Design decisions," above.
  - **Round 7 (done): CSP + the `middleware.ts`→`proxy.ts` migration** — described in Design decisions and Security above. Both builders' independent plans converged almost completely (identical directive shapes, and — most notably — the identical nonce-forwarding hazard in Supabase's `setAll` callback, found and fixed the same way by both before either saw the other's plan), leaving one genuine open question the ruling resolved directly: whether `'strict-dynamic'` should ship from the start (per Next's own documented nonce guidance, confirmed by this round's fact-gathering against the installed version's bundled docs) or be added only if a browser proved it necessary.
