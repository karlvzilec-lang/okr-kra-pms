# Brief: Goal/Rating creation UI (Round 1 of the gap-closure build)

## Context

Repo: `C:\Users\Mark Celiz\Documents\okr-kra-pms`. A brutal gap-audit found the single biggest hole in this system: **there is no UI anywhere for an employee to create/edit a goal, submit a self-assessment, or for a manager to submit a manager rating.** `/review` is 100% read-only. Every rating in the seed data was hand-written SQL. This round builds that missing core loop.

The facts below are pre-verified against the current schema (read in full, not recalled) — treat them as ground truth, do not re-derive independently:

### Schema facts (`supabase/migrations/0001_core_tables.sql`)

- `goal_plan_status` enum: `'draft', 'submitted', 'manager_reviewed', 'finalized'`. **No function or trigger anywhere in 0001–0016 transitions this value automatically.**
- `employee_goal_plan`: `id, review_cycle_id, employee_id, status, overall_rating_scale_max, created_at, updated_at`. No `published_at` here (that's Phase 3, a different concept — don't confuse the two).
- `kra_category`: `id, employee_goal_plan_id, name, description, weight numeric(6,2), created_at, updated_at`. Weight is a percent *within the plan*; comment on the column explicitly says the "sum to 100" check is deferred to `validate_goal_plan_weights` (0004), not enforced by a table constraint.
- `goal`: `id, kra_category_id, title, description, weight numeric(6,2), target_metric text, rating_scale_max integer default 5, self_rating numeric(5,2), self_comment text, manager_rating numeric(5,2), manager_comment text, created_at, updated_at`. Both ratings are nullable, each CHECK-bounded to `[0, rating_scale_max]` (not a fixed 1–5 range — `rating_scale_max` is per-goal). Weight is percent *within its category*.
- `review_participant` (0002): `employee_goal_plan_id, participant_id, role, created_at`, unique on `(employee_goal_plan_id, participant_id, role)`.

### RLS facts (`supabase/migrations/0003_rls_policies.sql`)

- `can_edit_goal_plan_as_employee(plan_id)`: true iff caller is the plan's `employee_id` **and** `review_participant` has them as `role='employee'` **and** `status in ('draft','submitted')`. This is the plan-level status gate.
- `can_manager_rate_goal(goal_id)`: true iff caller is a `role='line_manager'` participant on the goal's plan **and** the goal's `review_cycle.status = 'manager_eval'`. **This gates on `review_cycle.status`, a separate table/enum from `employee_goal_plan.status`.**
- `employee_goal_plan` RLS: `select` (HR or participant), `employee_update` (`using`: `can_edit_goal_plan_as_employee`; `with check`: employee_id matches, status in draft/submitted, is employee participant), `employee_delete`, `hr_all`. **No manager-role UPDATE policy exists on this table at all.** Only HR can currently move a plan to `manager_reviewed`/`finalized` — that's a real gap this round closes (see "New DB work" below). **No employee-INSERT policy exists either** — only HR can create a plan row (`hr_all`). This round does **not** change that: it assumes a plan (+ its `review_participant` rows) already exists (from seed data, or from a future admin UI — a later round) and builds the employee/manager editing experience on top of it.
- `kra_category` RLS: `select` (HR or participant), `employee_insert`/`employee_update`/`employee_delete` all gated by `can_edit_goal_plan_as_employee(employee_goal_plan_id)`, `hr_all`.
- `goal` RLS: `select` via `can_read_goal`. `insert` (`goal_employee_insert`): `with check (can_edit_kra_category_as_employee(kra_category_id))` — **only employees can insert goal rows; there is no manager-insert path** (managers rate existing goals, they don't create them). `update` (`goal_participant_update`): `using (can_edit_goal_as_employee(id) or can_manager_rate_goal(id))`, `with check (can_edit_kra_category_as_employee(kra_category_id) or can_manager_rate_goal(id))`. `delete`: employee-only, via `can_edit_goal_as_employee`.
- **`restrict_manager_goal_updates()` trigger** (before update on `goal`): HR bypasses; for a caller who qualifies as `can_manager_rate_goal(old.id)`, blocks changing anything except `manager_rating`/`manager_comment` (and `updated_at`, deliberately excluded from the check), raising `42501` otherwise. **There is no mirrored trigger restricting what an EMPLOYEE can write.** Concretely verified: because `goal_participant_update`'s `with check` only tests `can_edit_kra_category_as_employee(...) or can_manager_rate_goal(...)` — not which columns changed — an employee who passes `can_edit_kra_category_as_employee` can currently write **any** column on `goal` via a raw UPDATE, including `manager_rating`/`manager_comment`. **This is a real, live security gap. Close it as part of this round** — see "New DB work" #1.

### Function facts (`supabase/migrations/0004_rating_rollup.sql`)

- `validate_goal_plan_weights(plan_id)`: raises `23514` unless every category's weight sums to exactly 100 *within the plan*, and every category's goals' weights sum to exactly 100 *within that category*. Auth-gated (`42501` unless HR or plan participant).
- `compute_goal_plan_rating(plan_id, rating_type)`: calls `validate_goal_plan_weights` internally first; raises `23514` if any goal has a null rating of the requested type; raises `23514` if the plan has zero goals. Upserts into `goal_plan_rating` on conflict `(employee_goal_plan_id, rating_type)`. **Never triggered automatically by anything** — always called explicitly (seed.sql, verify.sql). A UI that changes ratings must call this itself if it wants `/review`'s existing rollup display to reflect anything new.

### Established idiom to follow (`supabase/migrations/0011_password_policy.sql`)

The column-scope pattern used everywhere in this repo (`restrict_manager_goal_updates`, `restrict_profile_self_updates`): `security definer`, `set search_path = ''`, HR/admin bypass returns `new` immediately, then an `if new.x is distinct from old.x or new.y is distinct from old.y or ... then raise exception '...' using errcode = '42501'; end if;` chain naming every column that must NOT change, paired with an RLS policy that gets the right caller to the trigger in the first place. Follow this exact shape for every new column-scope guard in this round — don't invent a different pattern.

## Scope

### New DB work (new migration `0017_goal_rating_workflow.sql`)

1. **Close the employee-side column-scope gap.** Add `restrict_employee_goal_updates()`, a `before update` trigger on `goal`, mirroring `restrict_manager_goal_updates()`'s exact shape: HR bypasses; for a caller who qualifies as `can_edit_goal_as_employee(old.id)`, **allow** changes to `title`, `description`, `weight`, `target_metric`, `rating_scale_max`, `self_rating`, `self_comment` (goal structure + self-assessment — both are legitimately employee-editable while the plan is draft/submitted, per the existing RLS design) and **block** everything else — specifically `kra_category_id`, `manager_rating`, `manager_comment`, `created_at` — raising `42501` if any blocked column changes. 2. **Let a line manager mark a plan reviewed.** Add a new RLS UPDATE policy `employee_goal_plan_manager_mark_reviewed` on `employee_goal_plan`: `using` — caller is a `role='line_manager'` participant on this plan (mirror the participant-lookup shape from `can_manager_rate_goal`, wrapped in a new helper `can_manager_mark_plan_reviewed(plan_id)` for consistency with the rest of this file's style) **and** the plan's `review_cycle.status = 'manager_eval'`; `with check` — same helper. 3. **Do not touch**: `employee_goal_plan_hr_all`, the insert policies on `employee_goal_plan`/`review_participant` (still HR-only — out of scope, a later round), anything in 0012–0016 (calibration/Phase 3 — unrelated table family, don't risk it).
